# Интеграции

## Mi Fitness (Xiaomi) — единственный источник данных о тренировках

Реализация — отдельный пакет `src/mi_fitness_sync`, используемый
порталом через `portal/sync.py` и `portal/routers/auth.py`. Это **не**
обёртка над официальным публичным API: ни OAuth, ни документированного
REST/GraphQL-эндпоинта у Xiaomi для сторонних интеграций нет. Пакет
воспроизводит протокол, которым пользуется мобильное приложение Mi
Fitness/Zepp — то есть реверс-инжиниринг закрытого API, который Xiaomi
может изменить без предупреждения.

### Авторизация

1. **Логин по паролю** (`MiFitnessAuthClient.login_with_password`,
   `src/mi_fitness_sync/auth/client.py:89`): запрос к Xiaomi Passport
   (`account.xiaomi.com/pass/serviceLoginAuth2`) с MD5-хешем пароля,
   сервисным ID `miothealth`, и «meta login data» (`_sign`/`qs`/
   `callback`), предварительно полученными отдельным GET-запросом.
   Ответ может вместо токена содержать требование капчи
   (`CaptchaRequiredError`), push/SMS-подтверждения
   (`NotificationRequiredError`) или дополнительного шага
   (`Step2RequiredError`) — портал прокидывает эти случаи наружу через
   `/api/auth/login` полем `action`.
2. **STS-обмен**: успешный логин даёт `passToken`, `ssecurity`, `nonce`
   и URL для STS-хендшейка; переход по нему с подписью
   (`_generate_client_sign`, HMAC-подобная SHA1-подпись на базе
   `ssecurity`) отдаёт `serviceToken` — именно он авторизует все
   дальнейшие запросы к данным о тренировках.
3. **Регион.** `MI_FITNESS_COUNTRY_CODE` (по умолчанию `RU`)
   переводится в один из региональных доменов Xiaomi
   (`region_mapping.py`: `ru`, `de`, `us`, `sg`, `cn`, `i2` и т.д.) —
   без него клиент один раз спрашивает регион по IP у самого Xiaomi и
   кэширует ответ на время жизни клиента.
4. **Хранение состояния.** Всё перечисленное (токены, `ssecurity`,
   `psecurity`, полный список cookies) сохраняется как есть в
   **незашифрованном JSON-файле** по пути `MI_FITNESS_STATE_PATH`
   (`src/mi_fitness_sync/auth/store.py`) — по умолчанию
   `~/.running_portal/auth.json`. Файл корректно добавлен в
   `.gitignore` и в репозиторий не попадает, но на диске лежит открытым
   текстом; шифрования состояния в коде нет (см. также
   `PRODUCTION_READINESS.md`, пункт «encrypt persisted Mi Fitness auth
   state»).
5. **Обновление сессии при `401`.** Сначала «тихий» рефреш через
   `refresh_auth_state` (повторная валидация `passToken` без пароля);
   если он не проходит и `MI_FITNESS_PASSWORD` задан — повторный логин
   по паролю. Без пароля в `.env` истёкшую сессию нужно обновлять вручную
   через `/api/auth/login`.

### Запросы к данным: подпись и шифрование

Каждый запрос к `hlth.io.mi.com` (список активностей, детали, FDS-ссылки)
идёт как `GET` с зашифрованным телом в query-параметрах
(`ActivityTransport.request_json`,
`src/mi_fitness_sync/activity/transport.py:123`):

1. Генерируется nonce (`generate_nonce`) и `signed_nonce =
   SHA256(ssecurity || nonce)`.
2. JSON-параметры запроса шифруются RC4-подобным потоковым шифром
   (`Rc4Cipher`, `src/mi_fitness_sync/activity/crypto.py`) с ключом
   `signed_nonce`.
3. Считается подпись `SHA1(METHOD & path & sorted(params) &
   signed_nonce)` — сначала для расшифрованных, затем ещё раз для
   зашифрованных параметров.
4. Ответ сервера расшифровывается тем же RC4-ключом
   (`decrypt_response_payload`).

Это тот же протокол, что использует официальное приложение Xiaomi —
никакого отдельного API-ключа для сторонних интеграций не существует;
секретом, по сути, выступает `ssecurity`, полученный при логине.

### Данные активности: два разных источника на один запрос деталей

`get_activity_detail` (`src/mi_fitness_sync/activity/client.py:121`)
комбинирует два независимых источника, и берёт то, что доступно:

- **JSON fitness data** (`/app/v1/data/get_fitness_data_by_time`,
  ключ `huami_sport_record`) — тот же зашифрованный JSON-протокол, что
  и список активностей; даёт `track_points`/`samples`, если устройство
  или приложение выгрузило их в этом виде.
- **FDS (File Distribution Service)** — отдельный эндпоинт
  (`gen_download_url`) выдаёт подписанные URL на бинарные файлы
  (GPS-трек, посекундные «sport records», сводный «sport report»,
  кривая восстановления пульса). Каждый файл:
  1. скачивается обычным `GET` по URL из ответа;
  2. расшифровывается AES (`decrypt_fds_data`,
     `src/mi_fitness_sync/fds/common.py`, фиксированный IV, ключ —
     `obj_key` из того же ответа);
  3. разбирается собственным бинарным TLV-парсером
     (`src/mi_fitness_sync/fds/gps_records.py`,
     `sport_records.py`, `sport_reports.py`,
     `recovery_rate.py`) — формат не документирован Xiaomi, типы полей
     заданы в коде числовыми константами (`TYPE_HR = 5`, `TYPE_PACE =
     12`, `TYPE_CADENCE = 49` и т.д., `fds/common.py:17`).

Если у активности есть и GPS-трек, и посекундные сэмплы из FDS, они
объединяются по времени (`merge_fds_samples_into_track_points`) — так
на графике детальной страницы пульс/каденс совпадают по времени с
точками GPS-трека.

Скачанные и расшифрованные FDS-файлы кэшируются на диске
(`FdsCache`, `src/mi_fitness_sync/fds/cache.py`) в
`MI_FITNESS_CACHE_DIR`, чтобы не перезапрашивать те же файлы повторно.

### Ограничения и хрупкие места

- **Неофициальный протокол.** Любое изменение на стороне Xiaomi
  (формат ответа, схема подписи, регионы) может сломать синхронизацию
  без отдельного уведомления; в коде это явно не версионируется.
- **Разбор `raw_report` — «подбор по нескольким именам».** Метрики
  активности (`pick_int`/`pick_float` в `portal/sync.py:66`)
  вытаскиваются по первому найденному из нескольких альтернативных
  ключей — признак того, что реальный формат ответа отличается между
  устройствами/версиями приложения и не был формально
  задокументирован даже внутри проекта.
- **Только бег.** Фильтр `category == "running"` в `portal/sync.py:306`
  — данные любых других видов тренировок из Mi Fitness синхронизацией
  отбрасываются на уровне портала (сам клиент `mi_fitness_sync` их
  умеет запрашивать).
- **Один регион на инстанс.** `MI_FITNESS_COUNTRY_CODE` — одна
  переменная окружения на весь портал; многопользовательский сценарий с
  разными регионами не предусмотрен.
- **Секрет сессии живёт в файле, не в БД.** `MI_FITNESS_STATE_PATH` —
  вне SQLite и вне бэкапа портала как такового; при переносе/бэкапе
  данных портала (`docs/deployment.md`) этот файл нужно переносить
  отдельно и по-прежнему держать вне репозитория.

## Claude Code CLI

Не источник тренировочных данных, а вычислительная интеграция для AI-тренера
— вызывается как subprocess, авторизуется через `claude auth login` или
`ANTHROPIC_API_KEY`. Подробности протокола вызова, входа/выхода трёх
AI-функций и обновления авторизации — в
[`docs/ai-assistant.md`](./ai-assistant.md) и
[`docs/workflows.md`](./workflows.md#обновление-авторизации-claude-cli).

## Прочие внешние сервисы

- **CDN Chart.js** (`cdnjs.cloudflare.com`) — единственная фронтенд-
  зависимость, подключается прямо в `templates/base.html`, без
  локальной копии в репозитории.

Других внешних интеграций (email/SMS-уведомления, Telegram и т.п.) в
коде нет — соответствующие идеи (Telegram-уведомления после синка,
утренняя проверка готовности) зафиксированы как нереализованные в
[`IDEAS.md`](../IDEAS.md).
